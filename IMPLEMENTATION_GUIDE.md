# Gym Tracker App - Implementation Documentation

## Overview
This is a comprehensive Flutter-based Gym Tracker application that allows users to log their workout sessions with a calendar-based interface. The app uses SQLite for persistent data storage, Provider for state management, and table_calendar for an interactive month view.

---

## Architecture & Component Structure

### 1. **Data Layer**

#### `lib/models/workout.dart`
Defines the `Workout` data model with the following properties:
- **id**: Unique identifier (auto-generated by SQLite)
- **date**: Workout date (normalized to midnight for consistency)
- **title**: Heading/title of the workout (displayed on calendar)
- **notes**: Detailed workout notes/description
- **createdAt**: Timestamp when workout was created
- **updatedAt**: Timestamp of last modification

**Key Methods:**
- `normalizeDate()`: Converts DateTime to midnight (removes time component)
- `toMap()`: Serializes Workout to Map for database storage
- `fromMap()`: Deserializes Map from database to Workout object
- `copyWith()`: Creates a copy with optional field updates

---

### 2. **Service Layer**

#### `lib/services/database_service.dart`
Handles all SQLite database operations using the `sqflite` package.

**Database Setup:**
- Path: `getDatabasesPath()/gym_tracker.db`
- Table: `workouts` with indexed date column for fast queries
- Auto-incrementing primary key for workout IDs

**Key Methods:**
- `saveWorkout()`: Insert new or update existing workout
- `getAllWorkouts()`: Retrieve all workouts from database
- `getWorkoutByDate()`: Fetch specific workout for a date
- `getWorkoutsInRange()`: Get workouts within date range
- `deleteWorkout()`: Remove workout by ID
- `closeDatabase()`: Clean up database connection

**Error Handling:** All methods wrapped in try-catch with descriptive error messages.

---

### 3. **State Management Layer**

#### `lib/providers/workout_provider.dart`
Uses `ChangeNotifier` from Provider package for reactive state management.

**State Variables:**
- `_workouts`: List of all loaded workouts
- `_selectedWorkout`: Currently selected workout (can be null)
- `_selectedDate`: Currently selected date
- `_isLoading`: Loading indicator flag
- `_errorMessage`: Error message for display

**Key Methods:**
- `initialize()`: Load all workouts on app startup
- `setSelectedDate()`: Select date and load its workout
- `saveWorkout()`: Save/update workout with validation
- `deleteWorkout()`: Remove workout from database and list
- `getWorkoutForDate()`: Get workout for specific date
- `getWorkoutsForMonth()`: Get all workouts in a month (for calendar display)

**Features:**
- Automatic UI updates via `notifyListeners()`
- Input validation (non-empty title required)
- Loading state management
- Error message handling

## Date Handling

**Key Principle:** All dates are normalized to midnight (00:00:00) to ensure consistent comparisons.

```dart
// Example: January 15, 2024 with any time component
DateTime date = DateTime(2024, 1, 15, 14, 30, 45);
DateTime normalized = Workout.normalizeDate(date);
// Result: DateTime(2024, 1, 15, 0, 0, 0)
```

This prevents issues where the same workout date might be stored with different times.

## Database Schema

```sql
CREATE TABLE workouts (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  date TEXT NOT NULL,           -- ISO 8601 format (midnight)
  title TEXT NOT NULL,          -- Workout heading
  notes TEXT NOT NULL,          -- Detailed notes
  createdAt TEXT NOT NULL,      -- ISO 8601 format
  updatedAt TEXT                -- ISO 8601 format (nullable)
);

CREATE INDEX idx_date ON workouts(date);  -- For faster queries
```

## User Workflows

### 1. **View Workouts (Launch)**
1. App launches → HomeScreen initialized
2. WorkoutProvider loads all workouts from database
3. Calendar displays workouts as event indicators
4. Current date is automatically selected

### 2. **Add New Workout**
1. User taps FAB or any date on calendar
2. WorkoutDetailsScreen opens with selected date
3. User enters workout title and notes
4. Taps "Save" button
5. Workout saved to database
6. HomeScreen reloads and displays new workout on calendar

### 3. **Edit Existing Workout**
1. User taps date with existing workout
2. WorkoutDetailsScreen loads with previous data
3. User modifies title/notes
4. Taps "Save" to update
5. Database updates, HomeScreen refreshes

### 4. **Exit Without Saving**
1. User taps "Cancel" button
2. If changes exist, confirmation dialog appears
3. User confirms to discard changes
4. Returns to HomeScreen

## Performance Considerations

- **Date Indexing**: Database index on date column for O(log n) lookups
- **Lazy Loading**: Calendar only renders visible months
- **Single Database Instance**: Singleton pattern prevents multiple connections
- **Event Loader**: Efficient computation of events per date
- **Scroll Performance**: SingleChildScrollView with bounded content
